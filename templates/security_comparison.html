Module E · Defence in depth

Who is responsible for what?

No single layer can stop SQL Injection and XSS on its own. Each layer adds a control; together they form defence in depth. The diagram shows how data travels through WebShield and where each control is applied.

Data flow

{% include "_architecture.html" %}
  1. 1
    Browser → Server. A form is submitted over HTTP with its CSRF token. HTML attributes (maxlength, pattern) give quick feedback.
  2. 2
    Server checks. Flask verifies the CSRF token and session, then validates type, length and format of every field again.
  3. 3
    Server → Database. SQL text with ? placeholders is sent together with the values as separate parameters.
  4. 4
    Database. SQLite enforces NOT NULL, UNIQUE, CHECK and FOREIGN KEY constraints and returns rows.
  5. 5
    Server → Browser. Jinja2 encodes every value (< → &lt;) and the response carries a strict Content-Security-Policy.
  6. 6
    Browser. JavaScript updates the page with textContent, never innerHTML, for untrusted values.
Layer 1

Client-side security

  • Basic input validation with required, maxlength, pattern — for usability.
  • Safe DOM manipulation: textContent, createElement, setAttribute.
  • Handle user content as text; never pass it to innerHTML, eval or document.write.
  • Never rely on the browser alone: anyone can bypass client checks with DevTools, curl or a proxy.
  • Respect the server's Content-Security-Policy (no inline scripts).

In WebShield: static/js/main.js

Layer 2

Server-side security

  • Input validation — allow-list format and length checks.
  • Authentication — salted scrypt password hashes.
  • Authorisation — login required for labs; users can delete only their own comments.
  • Parameterised SQL queries everywhere.
  • Context-aware output encoding (Jinja2 auto-escape).
  • Secure sessions — signed cookie, HttpOnly, SameSite=Strict, 30-min expiry, regenerated on login.
  • CSRF tokens on every POST form.
  • Generic error pages; debug mode off.

In WebShield: routes/, security/

Layer 3

Database security

  • Least privilege — the app account should only have the rights it needs (the lab sandbox is read-only via an authorizer).
  • Parameterised queries — the database compiles the statement before seeing values.
  • Integrity constraints — PK, FK, UNIQUE, NOT NULL, CHECK.
  • Secure password storage — only hashes produced by the application layer are stored.
  • Hide database errors — error messages reveal table and column names to attackers.

In WebShield: database/schema.sql
