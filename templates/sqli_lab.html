Module C · SQL Injection

Login bypass: string concatenation vs. parameterised queries

SQL Injection happens when user input is copied into the text of a SQL statement. Characters such as ' and -- then stop being data and become SQL syntax, letting the attacker rewrite the query. Below, the same input is sent to two login implementations. Both query an isolated in-memory test database containing only fictional accounts; the main WebShield database is never touched.

INTENTIONALLY VULNERABLE

Unsafe SQL construction

query = (
  "SELECT id, username, role FROM lab_users "
  "WHERE username = '" + username + "' "
  "AND password_hash = '" + sha256(password) + "'"
)
conn.execute(query)

The input becomes part of the SQL code. File: vulnerable/sqli_sandbox.py

SECURE IMPLEMENTATION

Parameterised SQL

query = (
  "SELECT id, username, role FROM lab_users "
  "WHERE username = ? AND password_hash = ?"
)
conn.execute(query, (username, sha256(password)))

The SQL text is fixed; values are sent separately as data.

Why the vulnerable version fails

With username ' OR '1'='1' -- the server builds:

SELECT id, username, role FROM lab_users WHERE username = '' OR '1'='1' --' AND password_hash = '...'
  • The first ' closes the string literal early.
  • OR '1'='1' is always true, so every row matches.
  • -- turns the password check into a comment.
  • The application logs the attacker in as the first user returned.

How parameterised queries prevent it

With placeholders, the database compiles the SQL first and only afterwards receives the values. The query structure is fixed before the input is seen, so ' OR '1'='1' -- is simply searched for as a literal username — which does not exist.

  • Use placeholders for every value, in every query.
  • Never build SQL with +, %, .format() or f-strings.
  • Apply least privilege: the app's DB account should not be able to drop tables.
  • Validate input (type, length, format) as an extra layer — not as the main defence.
  • Hide database errors from users; log them server-side.
