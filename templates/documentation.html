Vulnerability reference

A structured summary of each vulnerability: definition, mechanism, location, impact, demonstration and prevention. Jump to SQL Injection or Cross-Site Scripting.

SQLi SQL Injection

Definition
An injection flaw in which untrusted input is interpreted as part of a SQL command, allowing an attacker to change the logic of the query sent to the database. It belongs to OWASP Top 10 category A03: Injection.
How it works
The application concatenates input into SQL text. The database parser cannot tell which part was written by the developer and which came from the user. Quotes close string literals, keywords like OR or UNION add logic, and -- comments out the rest. 
SELECT * FROM users WHERE username = '' OR '1'='1' --' AND password = '...'
Where it happens
Any place input reaches a query: login forms, search boxes, URL parameters (?id=5), sorting/filter options, cookies and HTTP headers, and in stored data that is later reused in a query (second-order injection).
Why it is dangerous
Authentication bypass; reading confidential data (UNION-based or blind extraction); modifying or deleting data; in some database systems, reading files or executing operating-system commands. It directly breaks confidentiality, integrity and availability.
Practical demonstration
In the SQL Injection Lab, entering lab_admin' -- as the username logs into the fictional administrator account on the vulnerable version without a password, while the parameterised version refuses the login.
Prevention techniques
  • Parameterised queries / prepared statements (primary defence).
  • ORMs or query builders that parameterise automatically (and care with their "raw SQL" functions).
  • Allow-list validation for values that cannot be parameterised (e.g. column names for sorting).
  • Least-privilege database accounts; separate read and write accounts.
  • Generic error messages; detailed errors only in server logs.
  • Web Application Firewalls as an additional, not primary, layer.
Real-world examples (conceptual)
SQL Injection has been behind many large data breaches in which attackers extracted millions of customer records from retail, telecom and government websites through a single vulnerable parameter. Automated scanners continuously probe public sites for it, so even small applications are targeted.

XSS Cross-Site Scripting

Definition
An injection flaw in which untrusted data is included in a web page without proper encoding, so the victim's browser executes attacker-controlled script in the context of the trusted site. Also part of OWASP A03: Injection.
How it works
The browser cannot distinguish the site's own scripts from injected ones on the same origin. Injected <script> tags, event handlers (onerror, onload) or javascript: URLs run with the page's privileges.
  • Reflected: the payload is in the request (usually a URL) and echoed in the response. The victim is tricked into opening a crafted link.
  • Stored: the payload is saved (comment, profile, message) and served to every user who views it.
  • DOM-based: client-side JavaScript reads a source (location.hash, postMessage) and writes it to a dangerous sink (innerHTML, eval); the server may never see the payload.
Where it happens
Search result pages, error messages, comment sections, user profiles, chat applications, admin panels that display user data, and front-end code that builds HTML from strings.
Why it is dangerous
The script acts as the victim: it can read page content, perform actions (change e-mail, post content), steal non-HttpOnly session cookies, show fake login forms (phishing on a trusted domain), log keystrokes or spread itself as a worm through stored content.
Practical demonstration
In the XSS Lab, posting <img src=x onerror="alert('XSS')"> triggers an alert in the sandboxed vulnerable panel, while the secure panel shows the exact characters as text.
Prevention techniques
  • Context-aware output encoding (HTML body, attribute, URL, JavaScript, CSS each need different encoding).
  • Keep template auto-escaping on; avoid |safe, Markup() and innerHTML for untrusted data.
  • Use safe DOM APIs: textContent, setAttribute, createElement.
  • If rich HTML is required, sanitise with a maintained allow-list sanitiser.
  • Content-Security-Policy that forbids inline scripts (defence in depth).
  • HttpOnly session cookies to limit impact; validate input length and format.
Real-world examples (conceptual)
Stored XSS worms on social networks have spread to over a million profiles in hours by copying themselves into each viewer's profile. Reflected XSS in login or search pages of well-known sites has been used to hijack sessions and run convincing phishing pages on legitimate domains.
