Hash algorithms: integrity, passwords and why the choice matters

A hash function maps input of any length to a fixed-length output (the digest). It is one-way: you cannot compute the input back from the digest. WebShield uses hashing to store passwords (scrypt), to sign session cookies (HMAC) and in the SQL Injection sandbox (SHA-256). This lab shows the properties that make a hash secure and why passwords need a salted, slow hash rather than a fast one.

DeterministicThe same input always gives the same digest.
Pre-image resistantGiven a digest, finding an input that produces it is infeasible.
Collision resistantFinding two inputs with the same digest is infeasible.
Avalanche effectA one-character change flips about half of the output bits.

4 Work factor — fast hashes vs. password-hashing functions

General-purpose hashes are designed to be fast, which is right for file integrity but wrong for passwords: the faster one hash is, the more guesses per second an attacker with a stolen database can make. Password-hashing functions are deliberately slow and (for scrypt and Argon2) memory-hard.

5 Integrity with HMAC-SHA256

A plain hash proves nothing if an attacker can change both the message and its hash. HMAC mixes a secret key into the hash, so only the key holder can produce a valid tag. Flask signs WebShield's session cookie with HMAC (itsdangerous, HMAC-SHA1 by default — SHA-1 collisions do not break HMAC).
