Module D · Cross-Site Scripting

Unsafe rendering vs. output encoding

XSS occurs when untrusted data reaches the browser in a place where it is interpreted as HTML or JavaScript. Each demonstration below renders the same input twice: once unsafely inside a sandboxed iframe with an opaque origin (it cannot read WebShield's cookies, DOM or network), and once safely in the main application, where it is encoded and shown as plain text.

1Reflected XSSPayload in the request is echoed back immediately (e.g. a search term in the URL). 2Stored XSSPayload is saved in the database and served to every visitor. 3DOM-based XSSClient-side JavaScript writes untrusted data (e.g. URL fragment) into the DOM.

2 Stored XSS — comment system

Comments are saved in the SQLite comments table with a parameterised INSERT. The database stores exactly what was typed; safety depends on how the comment is rendered.

3 DOM-based XSS — client-side rendering

The server is not involved: a script reads location.hash and writes it into the page. Note that a <script> tag inserted with innerHTML does not run, but event handlers such as <img onerror> do.

{{ example_buttons('dom-input') }}
INTENTIONALLY VULNERABLE · sandboxed 
const v = decodeURIComponent(location.hash.slice(1));
out.innerHTML = "Hello, " + v;
SECURE IMPLEMENTATION 
const v = input.value;
out.textContent = "Hello, " + v;

How to prevent each type

TypeWhere the flaw isPrevention
ReflectedServer echoes request data into HTMLEncode output for its context (Jinja2 auto-escaping); validate length/format; CSP.
StoredServer renders saved data without encodingEncode on output (not only on input); never use |safe / Markup() on user data; sanitise with an allow-list library if rich HTML is truly required.
DOM-basedClient JavaScript writes to a dangerous sinkUse textContent, setAttribute, createElement; avoid innerHTML, document.write, eval; consider Trusted Types.
All—Content-Security-Policy without 'unsafe-inline', HttpOnly cookies, framework auto-escaping left on.
